# EvidenceGraph AI

### KPI Intelligence-to-Action Engine for E-Commerce
### Team HerForge · Accenture Innovation Challenge 2026 · Round 2 · Track 3: BusinessIntelligence.ai

---

## 1. Overview

EvidenceGraph AI is an intelligent anomaly investigation and decision-support engine designed for complex e-commerce operations.

Traditional dashboards are good at answering:

> "What changed?"

EvidenceGraph AI goes further and answers:

> "Why did it change?"
>
> "What evidence supports that explanation?"
>
> "Could something else be causing it?"
>
> "How confident are we?"
>
> "Should we ACT, INVESTIGATE, or ABSTAIN?"
>
> "What could happen if we intervene?"

The system combines deterministic analytics, statistical anomaly detection, evidence-graph reasoning, contradiction analysis, counterfactual simulation, RAG-based evidence retrieval, and LLM-powered natural-language explanation.

The central design principle is:

> **The LLM is never the source of quantitative truth.**

All quantitative outputs — KPI values, anomaly signals, confidence scores, causal rankings, PVM contributions, and intervention estimates — are generated by the backend analytical pipeline.

The LLM is used primarily as a conversational and narrative layer over already-computed evidence.

---

## 2. The Core Idea

EvidenceGraph AI follows an end-to-end decision workflow:

```text
DETECT
   ↓
VERIFY DATA
   ↓
IDENTIFY MATERIAL SIGNAL
   ↓
BUILD EVIDENCE GRAPH
   ↓
RANK ROOT CAUSES
   ↓
CHALLENGE THE HYPOTHESIS
   ↓
CALCULATE CONFIDENCE
   ↓
ACT / INVESTIGATE / ABSTAIN
   ↓
SIMULATE INTERVENTION
   ↓
RECOMMEND ACTION
   ↓
EXPLAIN THROUGH LLM
```

Instead of treating anomaly detection as the final output, EvidenceGraph AI treats it as the beginning of an investigation.

---

## 3. Why This Is Different From a Traditional Dashboard

A conventional dashboard might show:

```text
Revenue ↓ 12%
Cancellation Rate ↑ 8%
Fulfillment Delay ↑ 15%
```

The business user still has to manually determine what happened.

EvidenceGraph AI transforms this into:

```text
Revenue anomaly detected
        ↓
Data quality verified
        ↓
Fulfillment problem confirmed
        ↓
Warehouse staffing changed first
        ↓
Delay increased afterwards
        ↓
Cancellations increased
        ↓
Revenue declined
        ↓
Alternative explanations challenged
        ↓
Confidence calculated
        ↓
Recommended decision
```

This creates an evidence-backed investigation rather than a collection of disconnected alerts.

## 6. Backend Components

### 6.1 Multi-Source Reconciliation (`pipeline/reconciliation.py`)

Enterprise data comes from multiple systems with different schemas, granularities, timestamps, refresh frequencies, and entity identifiers.

The reconciliation layer aligns these sources into a common analytical representation.

Example sources:

| Source | Example Data |
|---|---|
| OMS | Revenue, cancellations |
| Logistics | Fulfillment delays |
| WMS | Warehouse staffing |
| Support | Customer ticket volume |
| Marketing | Marketing spend |

The resulting dataframe becomes the common input for downstream investigation.

### 6.2 Calendar Reconciliation (`pipeline/calendar_reconciliation.py`)

Calendar effects can create false anomaly signals.

The calendar reconciliation layer checks whether observed movements overlap with known calendar effects before treating them as operational anomalies.

This prevents the system from incorrectly blaming an operational driver for a movement caused by a legitimate calendar effect.

### 6.3 Data Reality Check (`pipeline/data_reality_check.py`)

Before investigating an anomaly, EvidenceGraph AI asks:

> "Is there enough reliable data to investigate this?"

Two gates are evaluated:

* **Gate 1 — Completeness**: Checks whether each source satisfies the required minimum completeness threshold.
* **Gate 2 — History**: Checks whether sufficient historical observations exist for the configured analysis.

If the required data-quality conditions are not satisfied: **ABSTAIN**. The system does not attempt to manufacture a root cause from insufficient data.

### 6.4 Materiality Engine (`pipeline/materiality.py`)

Not every KPI movement is meaningful.

The Materiality Engine identifies movements that are statistically and/or commercially meaningful.

The implementation combines statistical anomaly detection with business-impact considerations to prevent investigation of harmless noise while ensuring financially important movements are surfaced.

### 6.5 Evidence Graph (`pipeline/evidence_graph.py`)

The Evidence Graph represents the relationships between business KPIs.

For an operational scenario, an example chain looks like:

```text
Warehouse Staffing
        ↓
Fulfillment Delay
        ↓
Support Tickets
        ↓
Order Cancellations
        ↓
Revenue
```

The graph combines structural business relationships with data-driven evidence. The implementation also supports different evidence relationships and scenario-specific structures.

The graph is then used by the root-cause engine to rank potential drivers.

### 6.6 Root Cause Engine (`pipeline/root_cause.py`)

The Root Cause Engine evaluates candidate drivers using multiple signals, including:

* temporal precedence
* graph evidence
* effect size
* materiality
* PVM contribution
* candidate ranking

An important safeguard is that the target KPI itself is not allowed to become its own root cause.

PVM balancing items such as residual/quantity balancing components are also prevented from being incorrectly presented as causal drivers.

#### Zero-Variance Step-Change Handling

A specific edge case is handled for variables such as:

```text
500
500
500
500
560
560
560
```

The baseline standard deviation is 0. A conventional z-score approach cannot detect the change because division by zero is undefined.

The root-cause engine therefore detects deterministic step changes directly, allowing deliberate administrative changes (such as price changes, staffing policy changes, or threshold changes) to participate correctly in temporal root-cause ranking.

### 6.7 PVM Decomposition (`pipeline/pvm_decomposition.py`)

Not every revenue anomaly is an operational failure.

For multi-factor commercial scenarios, EvidenceGraph AI uses Price-Volume-Mix style decomposition to separate revenue movement into contributing components:

```text
Revenue Change
     │
     ├── Price
     ├── Volume
     ├── Mix
     ├── Marketing
     └── Seasonal
```

The PVM engine includes accounting-closure validation so the decomposition is financially grounded, preventing the system from forcing every revenue problem into an operational causal chain.

### 6.8 Challenge Engine (`pipeline/challenge_engine.py`)

The Challenge Engine is designed to challenge the leading explanation.

It checks for:

* **Intra-region contradictions** (e.g. Fulfillment delays ↑ but Revenue remains stable due to promotions or price changes).
* **Cross-region contradictions**: The system can compare the current region with dynamically computed summaries from other regions without relying on static demo values.

### 6.9 Confidence Engine (`pipeline/confidence.py`)

The Confidence Engine produces an inspectable confidence score combining:

```text
Data Quality (0.20) + Signal Strength (0.25) + Cross-Source Consistency (0.15) + Evidence Depth (0.20) + Causal Chain Integrity (0.20) = Confidence Score
```

The resulting score drives the decision gate:

* High confidence (>= 0.68) -> **ACT**
* Moderate confidence -> **INVESTIGATE**
* Insufficient evidence / Data quality failure -> **ABSTAIN**

The operative ACT threshold in the current implementation is **0.68**, exposed transparently in the response payload.

### 6.10 Intervention Sandbox (`pipeline/intervention_sandbox.py`)

The Intervention Sandbox answers:

> "What might happen if I change this controllable lever?"

For operational scenarios, users can simulate changes such as:

```text
Warehouse Staffing -> Fulfillment Delay -> Support Tickets -> Cancellations -> Revenue
```

The backend estimates downstream changes using historical relationships, reports model confidence, and avoids fabricating relationships when data is insufficient.

### 6.11 Action Engine (`pipeline/action_engine.py`)

Once a decision has been made, the Action Engine converts the investigation into a structured recommendation containing Action ID, Type, Title, Description, Owner, Priority, Estimated Impact, Preconditions, Risks, and Confidence.

### 6.12 RBAC / Persona Layer (`pipeline/rbac.py`)

EvidenceGraph AI supports three personas:

* **General Manager**: Sees overall business health, revenue, financial impact, confidence, root causes, recommended actions, and PVM analysis.
* **Operations Lead**: Focuses on fulfillment, staffing, delays, cancellations, and operational recommendations. Sensitive financial information is strictly restricted.
* **Data Analyst**: Gets deeper analytical information including raw scores, graph topology, correlations, detailed evidence, and analytical metadata.

RBAC is enforced in the backend response layer rather than merely hiding UI elements.

## 7. RAG + LLM Architecture

The LLM layer is deliberately separated from quantitative reasoning:

```text
Backend Analytics -> RAG Retrieval -> LLM Narrator -> Human-readable answer
```

* **What the LLM does**: Answers user questions, explains mechanisms, formats recommendations, and summarizes evidence.
* **What the LLM does NOT do**: Calculate revenue, compute confidence scores, generate PVM contributions, or rank causal drivers.

## 8. Evidence Retrieval (`rag/retriever.py`)

The retrieval layer searches relevant qualitative evidence such as support tickets using embedding-based retrieval with sentence-transformers and cosine similarity, falling back to keyword matching when required.

## 11. Scenarios Detailed Walkthrough

* **Region A (Operational Chain)**: Demonstrates end-to-end operational anomaly propagation from warehouse staffing drop to revenue loss.
* **Region B (Contradiction)**: Demonstrates detection of compensating promotional discounts that mask operational delays.
* **Region C (Data Quality)**: Demonstrates automatic abstention when data sources have missing transaction logs.
* **Region D (Sparse History)**: Demonstrates abstention when history is below the 14-day minimum requirement.
* **Region E (Multi-Factor PVM)**: Demonstrates commercial factor attribution isolating Unit Price as the primary driver.

## 15. Running the Project Locally

### Backend Setup
```bash
cd engine
python -m venv venv
# On Windows:
venv\Scripts\activate
# On macOS/Linux:
source venv/bin/activate

pip install -r requirements.txt
python data/generate_synthetic.py
python -m uvicorn main:app --reload --port 8000
```

```bash
cd frontend

npm run dev
```
Frontend runs at `http://localhost:3000`.
